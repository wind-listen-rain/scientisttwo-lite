# 制作过程

时间均为北京时间（UTC+8）。每条都写了做了什么、为什么这么做、踩到的坑。后来接手的人请在末尾接着追加。

## 2026-09-27

**调研阶段（白天）**
- 调研 GitHub 上两个同名的 open-science 项目（aipoch / ai4s-research）。拿 ResearchClawBench 的原始数据逐题配对，
  发现它们在同模型下比极简基线只高约 2 分（满分 100），统计上不显著；又用同一个模型跑了三组文献综述实验，
  自动核验了全部引用。结论：轻量外壳的提升主要在工程层面，不在研究质量。
- 读 ScientistTwo 论文（arXiv 2609.19644）。抽查它放出的 5 篇生成论文：221 条引用全部真实，
  但正文都没有声明是 AI 生成，其中 2 篇的页眉印着"已在 ICLR 2025 发表"。
- 确认论文公开了流程骨架和各环节的次数上限，没公开提示词和审查标准；写稿组件 PaperOrchestra 有 Google 官方开源版本，
  任务清单来自开源的 AutoSOTA。判断：骨架可以还原，审查标准要从附录 B 的判例反推。

**选题（约 19:00）**
- 条件：在 ScientistTwo 的 107 道题里、它放出了对应论文、原代码公开、Mac 的 CPU 能跑。筛出 TreeHFD、M3SVM、OLLA 三个候选。
  选 TreeHFD 的理由：Apache-2.0 许可、仓库小而且还在维护、AutoSOTA 也做过这道题，可以三方对比。
- 发现 AutoSOTA 在这道题上的"−36.6%"靠的是用 3 个种子各抽一份训练数据、训 3 个模型再平均，等于训练数据变成 3 倍，
  但它的记录里写着"未违反红线"。于是评测按原论文协议重建，不用 AutoSOTA 的脚本。
- 读 ScientistTwo 的 ECTS-HFD 论文，发现它正文的主表只报训练集残差（接近 0），附录 Table 5 的留出集残差
  在 9 个数据集上全部比 TreeHFD 差。所以我们的评测同时报训练集和留出集。

**搭评测（19:30–20:10）**
- 坑 1：xgboost 在 macOS 上要 libomp，机器上没有 Homebrew → 用项目内 conda 环境从 conda-forge 装 llvm-openmp，不动已有环境。
- 下载 9 个 UCI 数据集，按论文的 n、p 反推特征选择。Abalone 起初多一列，改成 one-hot 去掉一列后 p=9，和论文一致。
  "Nutrition" 推断为 NHANES 年龄预测子集（n、p 都对得上）。
- 基线复现：子集 74 秒，全量 20 分钟（Superconductivity 一个数据集就要 12 分钟）；η(1,2)=0.033（论文 0.04），
  正交性、残差和论文同量级。

**编排器与空跑（20:10–20:30）**
- 写 orchestrator.py 和 24 个角色的提示词；空跑时所有智能体换成假的，但评测是真跑，52 次调用走遍了所有分支。
- 坑 2：Claude Code 的 Bash 工具会加载 `.zshrc`，里面的 conda init 会把 base 环境排到 PATH 最前面 → 提示词里一律写解释器的绝对路径。
- 坑 3：笔记本拔了电源后评测慢了 5 倍（系统降频）→ 插电运行，并用 caffeinate 防止空闲休眠。
- 改进：攒够成功想法后当轮就提前结束（原版就是这样）；消融变体改成 3 个并行评测（分解是单线程的）。

**真跑（20:30 起）**
- 20:35–20:56：找到 5 条局限，都落到了具体代码上（例如"最小二乘求解从不检查是否收敛，tree.py:115""稀疏格子没有收缩"）；
  生成 4 个种子想法，新颖度 6/5/3/3。
- 21:20 坑 4：碰到订阅的会话上限，写代码的智能体返回"You've hit your session limit"，编排器解析不到 JSON 就崩了。
  → 加上自动等待：识别"resets 10:40pm"这类提示，睡到重置时间再重试；等待时间不计入 12 小时预算；
  被打断的半成品先提交快照，并告诉智能体接着做。22:42 续跑。
- 23:10–23:41：S4 实现完成。子集审查员判"需要改进"，指出 Abalone 留出集正交性恶化 173%，而且写代码的智能体的解释"只是断言、没有验证"。
  工程智能体用多种划分和 bootstrap 复查，证明是划分带来的噪声；又用消融证明"整体级收缩偏移"这一步是必要的，
  方法本身一行没改。第二次审查通过，全量评测 6 分钟（比基线快 3 倍），全量审查通过。
- 坑 5：进度监控的管道里 `cut` 会缓冲输出，事件一直卡着没出来 → 改用 `awk ... fflush()`。

## 经验

1. **评测必须在智能体手够不着的地方**：子进程隔离、只读、哈希校验、官方分数只认编排器跑的。这几层都没被触发过，
   但正因为有它们，审查员才敢相信表格。
2. **干净上下文的审查员确实有用**：三次抓到真问题，都是写代码的智能体自己在 NOTES.md 里"合理化"掉的取舍。
3. **工程智能体会先验证再改**：面对审查员没有证据支撑的假设，它做了反驳实验而不是盲目改代码。
   这是最像人类研究者的一环。
4. **订阅额度是最大瓶颈**：写代码的 Opus 调用每次 20-30 分钟，一个额度窗口只够做一两个想法。
5. **"通过审查"不等于"真的更好"**：S4 的增益在新种子上成立，但它是取舍，不是全面胜出。
   这类判断最终还得靠独立复核和人来看。
